# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

`dicebattle` is an early-stage project and not a git repository. All nine tasks are done: the game is complete and playable (scaffold, rule engine, battle logic, sprites, title/help/select/game-over screens, dice throwing and rolling, the full turn presentation with poses and Critical!/FAIL! banners, AI turn, round clear, and Pause). Rule numbers (damage, heal amounts) are tuned often; the single source is `src/game/rules.ts` and the Korean summaries in `src/game/characters.ts`, and `docs/Spec.md` / `docs/PRD.md` must be updated with them.

- Game requirements and rules live in `docs/Spec.md` (source of truth); `docs/PRD.md` restates them as numbered requirements and acceptance criteria. Read Spec.md before implementing anything and keep both in sync when rules change.
- Work is split into `docs/tasks/task1.md` ... `task9.md`. Each lists its prerequisites and a checklist of completion conditions. Do them in order, and tick a checkbox only after verifying it. The user does the final check before the next task starts.
- Chosen stack: HTML5 Canvas + TypeScript, built with Vite (no React; every screen is drawn on the canvas). Logical resolution is 1280x720, scaled to the window. Unit tests use Vitest. Supported browsers: latest Chrome, Edge, Firefox.

## Commands

- `npm run dev`: Vite dev server
- `npm run build`: type check (`tsc --noEmit`) then production build
- `npm run test`: run all Vitest tests once (`npm run test:watch` to watch)
- `npm run assets:build`: convert the original sprite PNGs to the 600px WebP copies in `public/sprites/` (rerun after changing a PNG or `src/data/sprites.json`); `npm run assets:check` only verifies the originals exist
- One test file: `npx vitest run src/core/loop.test.ts`; one test by name: `npx vitest run -t "pattern"`

## Code layout

- `src/core`: constants, viewport math (`computeViewport`, `screenToLogical`), fixed-step `GameLoop`, `Scene`/`SceneManager` (scenes are created by name with typed params, see `src/scenes/types.ts`), `attachPointerInput` (Pointer Events -> logical coordinates, pointer captured so release outside the canvas still arrives), `createGameRng` (the only place a seed is chosen; `?seed=N` makes a game reproducible), `approach`/`clamp`
- `src/game`: pure rule/battle logic with no DOM, Canvas or timer imports (enforced by `purity.test.ts`), so it can be tested with seeded dice. All randomness goes through an injected `Rng` (`createRng(seed)`); never call `Math.random` in here.
  - `characters.ts`: stats and Korean names/intros for warrior, rogue, mage
  - `rules.ts`: `resolveAttack/resolveHeal(character, rng)` roll and evaluate; `evaluateAttack/evaluateHeal(character, dice, extraDice?)` evaluate fixed dice. Both return an `Outcome` (`rolls`, `kind` damage/heal/selfKO, `amount`, `critical`, `fail`, Korean `description`). A rogue whose first two dice have the same parity throws extra dice (2 when attacking, 1 when healing; `extraDiceCount`) that are appended to `rolls`, so `evaluateAttack/evaluateHeal` need `extraDice` in that case. The attack's 4 dice are judged by how many share a face (`faceGroups`: 75 / 30 / 50 / sum). `Battle` applies them.
  - `battle.ts`: `new Battle(playerCharacter, rng)` holds one run (round, HP, phase). Drive it with `playerAction('attack'|'heal')` -> `enemyAction()` -> (when `state.phase` is `roundCleared`) `startNextRound()`; `reset(character?)` restarts. Each call returns `BattleEvent[]` (`turn`, `rolled`, `damaged`, `healed`, `selfKO`, `roundCleared`, `gameOver`, `roundStarted`) for the UI to animate and log; it throws if called in the wrong `phase` (`playerTurn`, `enemyTurn`, `roundCleared`, `gameOver`). It owns HP clamping (0..max), the AI's random action, the uniform enemy pick, and the round-clear heal `floor(maxHp / 2)`. Mage 1,1,1 is a `selfKO` and 2,2,2 / 4,4,4 a `selfDamage` (25, event `selfDamaged`, FAIL! and the `fail` pose): if the actor's HP reaches 0 the player's ends the game, the AI's clears the round.
- Help screen layout lives in `helpLayout()`, `columnRows()` and `stepRows()` in `helpScene.ts` (margin 40, gutter 24, vertical gap 16, panel padding 24, 21 px rows) and is covered by `helpScene.test.ts`; change the numbers there, not in the draw code.
- `src/scenes`: `title`, `help`, `characterSelect`, `game`, `gameOver`, plus a dev-only `spritePreview`. `main.ts` loads the sprites, registers the scenes and starts `title`.
- The rogue's extra dice (a pair for attacks, one die for heals) are a separate stage in `DiceTray`: the first pair lands in the normal 2-dice layout (so nothing hints at more dice), then a bonus stage (`BONUS_*` constants, `bonusPhase`, `DieAnim.bonus`, `placeholderFrom`) pops the pair, shows "한 번 더!", slides it aside, shows dashed "?" slots (one per extra die) and only then throws the extra dice. `onSettled` still fires once, after the extra pair.
- `src/render`: `diceTray.ts` (the dice area: `DiceTray` state machine ready -> charging -> rolling -> settled, `holdToPower`, `layoutSlots`; the faces are always passed in, the hold time only shapes the animation; it uses its own cosmetic `Rng`, never the game's) and `dice.ts` (`drawDie`, pip layout), `setupCanvas` (window scaling, device pixel ratio), `sprites.ts` (loading, `drawSprite`, `placement`), `text.ts` (`drawText`, Korean-friendly `wrapLines`), `ui/` (`Button` = hover/press/click logic + drawing, `ButtonGroup`, `drawHpBar`, `LogBuffer`/`drawLogWindow`, `characterCard.ts` = the tall colored select card with `CARD_THEMES`, `cardRect`, `hpSegments`; the select card has no button, the whole card is the button; it shows the one-line `description` and 4-5 `cardRules` rows per character, while the full `rules` lists are on the help screen. Keep each card rule and the description at most 28 characters so they stay on one line). All drawing and hit-testing use logical 1280x720 coordinates.
- `src/data/sprites.json`: per-pose sprite settings (see Assets). `scripts/`: `build-sprites.mjs` (PNG -> WebP) and `measure-sprites.mjs` (dev helper).
- `src/game/messages.ts`: `formatEvent` turns a `BattleEvent` into the Korean log line.
- Dev shortcuts (dev server only): `?scene=game&p=mage&seed=13` jumps to a game, `?scene=sprites` (add `&view=duel&p=warrior&e=mage&pose=attack`) shows the sprite alignment tool.
- `GameScene` runs the whole turn presentation. Modes: `choose` (buttons on) -> `throw` (dice area on) -> `busy` (dice rolling, result shown, AI acting: all input ignored) -> back to `choose`, or `ended` once the player is down. A special result (critical or fail) first runs an explain step (`EXPLAIN_MS`): the settled dice pop one by one with a golden glow (`DiceTray.startHighlight`, `highlightFrame`) and the rule explanation shows under the dice (`explain`, `drawExplanation`); only afterwards come the pose, the big "Critical!"/"FAIL!" word and the impact. Plain results skip it. The dice area (`TRAY_RECT`, 360x270) is centered between the Pause button's bottom edge (y 130) and the log's top edge (y 520), 60 px each side; if either moves, re-center it and update the `dice area position` test. Each result is a `TurnPlan` (`scenes/turnPlan.ts`: `describeTurn(events)` gives the actor pose, victim, "Critical!"/"FAIL!" banner and ending) played by a `Sequencer` (`core/sequence.ts`, steps advanced only by dt so Pause freezes it): actor pose + banner -> impact (HP bars, log, `hit` pose, shake) -> back to idle -> next. `critical_*` poses and "Critical!" come from `outcome.critical`; `fail` and "FAIL!" from `outcome.fail`, never together. `Battle` already holds the result when the dice are thrown, so the scene keeps a separate `view` (HP, round, enemy) that is updated from events only at the impact step; never draw from `battle.state` directly or the result is revealed early. The HUD is drawn after the sprites so big effects never cover the HP bars. Pause: the Pause button (or the Escape key, via `Scene.onKeyDown` / `SceneManager.keyDown`, wired in `main.ts` with key repeat filtered) opens a menu (이어하기 / 재시작 -> `characterSelect` / 타이틀 -> `title`) and calls `app.setPaused(true)` (`AppContext`), which sets `loop.paused`; the scene also ignores `dt` while `paused`, only the menu takes input, and `exit()` always un-pauses, so restarting or leaving can never leave the loop frozen. Every scene change builds a brand-new `GameScene`, so a new game has no old state (round 1, full HP, empty log).
- `GameLoop` calls `update(dt)` at a fixed 60 Hz and `render(alpha)` every frame. Setting `loop.paused = true` (done through `AppContext.setPaused`) makes update receive `dt = 0`, so every animation timer must advance from that dt (never from wall-clock time `setTimeout`/`performance.now`) or Pause will not freeze it.
- In dev, `window.__dicebattle` exposes the loop, scene manager and canvas for inspection.

## Assets

Character sprites are 1254x1254 RGBA PNGs (transparent background, about 1.3-3 MB each) in `assets/characters/<Character>/<character>_<pose>.png`, for `Warrior`, `Rogue` and `Mage`.
- Poses: `idle`, `attack`, `critical_attack`, `heal`, `critical_heal`, `hit`; the Mage also has `fail` (the 1,1,1 self-KO). Always use `critical`, never `special`.
- `critical_*` is shown when a character's special dice condition fires (the "Critical!" message); otherwise use plain `attack`/`heal`. The Mage's 1,1,1 uses `fail` and the "FAIL!" message.
- Warrior and Rogue sprites face the left of the screen. The player stands on the left, so flip the player's sprite horizontally and draw the AI's on the right unflipped. `mage_attack.png` faces right, the opposite of the other Mage poses, so keep a per-pose facing flag instead of flipping by character.
- Poses differ in character size and position (the `critical_*` poses are mostly effects). Do not edit the PNGs to fix this: `src/data/sprites.json` gives each pose a `scale` (relative to `baseDisplaySize`, chosen so the head size matches idle), an `anchor` (torso centre as fractions of the image) and the original `facing`. `drawSprite(ctx, sprites, character, pose, x, y, facing)` draws the anchor at (x, y) and mirrors around it when needed, so all poses share one body position.
- The PNGs are the originals and are never modified. The game loads the 600px WebP copies from `public/sprites/` (generated, 36 MB -> 2 MB).

## Look and feel

Every screen shares one style, modeled on the character select cards: dusk-fantasy backdrop (`render/background.ts`: cached gradient sky, nebula, light shafts, castle and mountains, vignette, plus per-frame twinkling stars and drifting lights; `drawFloor` and `drawPlatform` build the battle stage), glass panels (`ui/theme.ts` `drawPanel`), glossy 3D buttons with color presets (`BUTTON_STYLES` gold/blue/red/green in `ui/button.ts`), the in-game HUD (`ui/hud.ts`: `drawHud` portrait + HP gauge with a damage/heal trail via `splitBar`, `drawRoundBadge`, `drawHeading`) and per-character colors (`CARD_THEMES`). Scenes keep their own `time` (ms, advanced from `update(dt)`) and pass it to `drawBackground(ctx, time)` so the backdrop freezes with Pause.

**Performance rule:** blur shadows (`shadowBlur`), big gradients and large clipped areas are slow to repaint every frame, especially in Firefox (it dropped to ~34 fps before this was fixed). Anything static goes through `render/cache.ts` (`cachedLayer(key, w, h, pixelScale(ctx), paint)` paints once into an off-screen canvas and reuses it; `drawPanel` does this per size and style). Do not call `drawPanel` with a style that changes every frame (that would fill the cache); animate with a plain stroke on top instead, as the dice tray's pulsing border does. In per-frame code prefer stacked translucent shapes over `shadowBlur`.

## Fonts

Text is drawn with two bundled Korean game fonts, both SIL OFL (licenses in `assets/fonts/`): **Jua** for body/UI (`FONT_FAMILY`) and **Black Han Sans** for titles, banners and big headings (`FONT_DISPLAY`, set with `display: true` in `drawText`/`setFont`), and **Titan One** (`FONT_LOGO`, Latin only) just for the "Dice Battle" logo on the title screen. Neither has a bold weight, so there is no `bold` option (faux bold looks smeared). The full TTFs in `assets/fonts/` are subsetted to the characters used in `src/**/*.ts` (plus ASCII) by `npm run fonts:build` into `src/assets/fonts/*.woff2` (about 80 KB total); `src/fonts.css` declares them and `main.ts` waits for `loadFonts()` before the first frame so canvas text never falls back. **After adding any new Korean text or symbol to `src/`, run `npm run fonts:build`** (the `fonts.test.ts` coverage test fails otherwise). Jua draws a comma like a period at small sizes, so write number lists as `6, 6, 6`, not `6,6,6`.

## Verifying in a browser

Browser checks (what the unit tests cannot cover) were done with headless Chrome, Edge and Firefox driven through `puppeteer-core`; the dev server must be on, and `?scene=game&p=<character>&seed=<n>` makes a game reproducible. Pick seeds that produce the case you want by searching with `Battle` + `createRng` in a throwaway Vitest file.
